# Task 3 · Browse and recover originals

Read the design, common plan and Task 2's finalized snapshot/receipt format. Implement in the isolated checkout. Use synthetic local fixtures and a fresh recovery state directory. Coordinate bridge and desktop integration with the other tasks.

**Deliverable.** “Restore files” in the source dashboard and “Recover from a recovery file” on the first setup screen lead to one browser. Show dated folders, immediate children and a breadcrumb; allow selecting the whole backup, a directory or an individual file. Select an existing ordinary parent for a new recovery folder, review the source/date/destination and run; show the verified output location or a specific retry action.

**Files.** Add `src/shared/NetCrate.Restore.psm1`, `src/desktop/RestoreView.cs`, `tests/installation/Test-OriginalsRestore.ps1` and `tests/desktop/RestoreViewTests.cs`. Modify `install/Invoke-SetupAction.ps1`, `src/desktop/setup/{WindowsSetupService,SetupState,SetupView}.cs`, `src/desktop/{SetupStartup,WindowView}.cs`, `src/desktop/Build.ps1` and `docs/setup.md`. Keep the independent tool bootstrap in `install/NetCrate.Dependencies.psm1` if a recovery-only tool selector is needed.

**Action interface.** `ListBackups`, `ListBackupChildren`, `RestoreSelection`. The request has either installed source context or the two recovery-only paths `RecoveryFile` and `RepositoryPath`. Browse inputs carry an exact full `SnapshotId` and an optional literal project-relative `RelativePath`; an empty relative path selects the backed-up folder. Restore takes `DestinationParent`. Return typed `Items` and `NextCursor` for bounded pages, or `RestoredPath` after verified publication, on the existing Succeeded/Code/Message envelope. Never serialize the recovery record itself over the bridge. Set an action-appropriate timeout/cancellation behavior for a long restore; keep caller/child lifetime and staging cleanup consistent.
